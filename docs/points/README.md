# Alpha point manifest

Первая коллекция точек нужна только для ограниченной проверки Ижевска. Она не должна связывать доменную модель с конкретным брендом или map provider.

## Поля

| Поле | Назначение |
|---|---|
| `id` | стабильный внутренний UUID/slug, не provider ID |
| `name` | отображаемое имя на момент импорта |
| `latitude`, `longitude` | канонические WGS84 координаты |
| `source` | источник координат |
| `source_id` | идентификатор записи источника |
| `source_url` | проверяемая ссылка/provenance |
| `license` | условия использования источника |
| `verification_status` | `source_checked`, `field_verified`, `rejected` |
| `verified_at` | время последней проверки |
| `notes` | безопасный комментарий без персональных данных |

## Правила

- Provider ID никогда не является primary key домена.
- Изменение имени или координат не переписывает исторические check-ins.
- Alpha использует bounded вручную просмотренный набор; автоматический импорт в приложение запрещён.
- Точка не попадает в полевой рейд до `field_verified` или явного owner-approved исключения.
- Архивирование запрещает новый обычный чекин, но сохраняет историю.
- Источник и лицензия хранятся вместе с manifest.
- Нельзя заявлять партнёрство или официальное одобрение бренда без доказательства.

Файл `alpha-points.csv` содержит 27 source-checked кандидатов из OpenStreetMap/Nominatim на 2026-08-28. Данные OpenStreetMap доступны по лицензии ODbL; приложение обязано показывать требуемую атрибуцию. Центроиды ways/relations не считаются готовыми geofence: каждый кандидат проходит полевую проверку безопасной точки подхода перед сменой статуса на `field_verified` и закрытием #30.

Все 27 текущих строк намеренно остаются `source_checked`: это импортируемый preview, а не утверждение о состоявшейся полевой проверке. Основной CSV сохраняет стабильный импортный контракт. Версионированные доказательства полевой проверки хранятся отдельно в `alpha-points-field-evidence.v1.csv`.

## Полевое доказательство v1

Строка получает статус `field_verified` только при наличии строки с тем же `point_id` в evidence-манифесте. Валидатор требует:

- `schema_version=1`;
- измеренные WGS84 `measured_latitude` и `measured_longitude` в alpha-границах Ижевска; основной manifest должен использовать эту безопасную точку с допуском форматирования до `0.000001°`;
- положительную `gps_accuracy_m` не хуже 50 м;
- `measured_at` в ISO 8601 с явной временной зоной; это же значение записывается в `verified_at`;
- `safe_stop_outcome=approved`; варианты `relocate` и `rejected` можно зафиксировать как результат выезда, но они не разрешают `field_verified`;
- SHA-256 содержимого закрытого evidence-пакета и непрямую ссылку вида `restricted/...`.

В репозиторий не добавляются исходный GPS-трек, фотографии, видео, EXIF или публичная ссылка на них. Evidence-файл содержит только хеш и непрозрачный restricted ref; доступ к самому пакету остаётся вне репозитория. Порядок выезда и шаблон записи описаны в [field-verification-worksheet.md](field-verification-worksheet.md).

## Импорт в alpha-Кабанду

После миграций укажите существующую Кабанду и email её owner в локальном `.env`, затем запустите импорт:

```dotenv
ALPHA_KABANDA_ID=00000000-0000-0000-0000-000000000000
ALPHA_OWNER_EMAIL=owner@example.com
```

```bash
pnpm --filter @kabanda/api points:import
```

Команда печатает JSON-отчёт с `reportId`, `collectionId`, `rowCount` и признаком `replayed`. Повторный запуск того же manifest безопасно возвращает прежний отчёт; изменение содержимого под тем же ключом отклоняется. Статус `source_checked` разрешает только просмотр кандидата и сам по себе не открывает полевой check-in.

Перед импортом и после изменения любого из двух manifest-файлов запустите:

```bash
pnpm test:points
```
