# Прямой HTTPS с резервным Storage Relay

Исследовано 18 сентября 2026. Предложение; переключение пока не включено.

## Текущее состояние

PWA на kabanda.website.yandexcloud.net передаёт запросы через Storage Relay.
`apps/pwa/src/lib/api-transport.ts` шифрует запрос и переносит opaque-сессию внутри него.
`apps/api/src/relay-bridge.ts` принимает envelope на `/relay/v1/request`, проверяет
идентификатор и fingerprint, переиспользует результат при повторной доставке.
В рабочей конфигурации сервер слушает 127.0.0.1:3099. Публичного HTTPS маршрута
для него нет; существующие Caddy-маршруты принадлежат другим приложениям.

## Предлагаемая схема

Добавить отдельный HTTPS hostname Кабанды и узкий reverse proxy к существующему
`/relay/v1/request`, плюс health endpoint. Разрешить CORS только origin приложения,
POST/OPTIONS и Content-Type; cookies не нужны. Не публиковать внутренние API,
Postgres, служебную конфигурацию или чужие приложения. Нужен стабильный hostname
с управляемым DNS и действительным сертификатом.

Первый небольшой запрос пробует прямой канал. При сетевой ошибке либо истечении
короткого лимита ожидания (начальное значение 2 секунды, уточнить по замерам)
отправляется **тот же envelope с тем же id и ключом** через Storage Relay.
Прямой путь при этом мог уже исполнить действие: создание нового id недопустимо.
Оба пути обязательно попадают в один replay store. Текущий store в памяти одного
процесса не даёт гарантии exactly-once после рестарта: для неидемпотентных операций
нужна проверенная прикладная дедупликация либо durable replay перед включением.

Успешный расшифрованный ответ приложения, включая 401/403/409/422, не является
причиной переключать транспорт или повторять бизнес-операцию. Отмена пользователем
отменяет оба пути; смена identity делает старый ответ непригодным, как сейчас.

При провале direct временно предпочитать Storage (например 60 секунд), затем
проверять direct безопасным запросом. Проверки объединять между параллельными
запросами. При online/возврате приложения на экран повторно проверять доступность;
не пытаться угадывать VPN. Если недоступны оба канала, сохранять существующие
локальные очереди и показывать офлайн-состояние.

Большие тела и ответы сейчас используют presigned blobs в Storage. Первый этап
ускорит API-запросы, но не уберёт эту зависимость для медиа. Полностью прямую передачу
фото нужно спроектировать отдельно с лимитами и теми же ключами дедупликации.

## Проверки перед включением

- прямой доступ, заблокированный direct, медленный ответ и переключение сети;
- direct исполнил мутацию, ответ потерялся: fallback не дублирует действие;
- login/logout, смена аккаунта во время запроса, отмена, ошибки приложения;
- недоступность обоих каналов и восстановление GPS/check-in/media очередей;
- рестарт сервера между попытками и гарантии дедупликации;
- реальные телефоны: Wi-Fi, мобильная сеть с ограничениями, VPN включён/выключен;
- измерить задержки; включать с конфигурационным флагом и возможностью отката.
