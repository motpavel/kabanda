# Прямой HTTPS с резервным Storage Relay

Реализовано 18 сентября 2026. PWA остаётся на kabanda.website.yandexcloud.net.
Публичная настройка `VITE_DIRECT_RELAY_URL` включает прямой канал; без неё остаётся
прежний Storage Relay. Первый рабочий адрес: https://93.77.181.109.nip.io/kabanda/relay/v1.
Используется существующий HTTPS-сертификат сервера. Доступность DNS nip.io —
дополнительная внешняя зависимость прямого канала; Storage от неё не зависит.

## Выбор канала

`direct-channel.ts` проверяет health с лимитом 1,5 с, объединяя одновременные проверки.
Успешная проверка сохраняется на 60 с. Запрос идёт прямо с лимитом 2,5 с, включая
чтение тела ответа. При сетевом сбое, ошибке внешней доставки или повреждённом
шифротексте **тот же envelope/id/key** отправляется через Storage. После сбоя direct
не проверяется следующие 60 с. Online/возврат видимой страницы сбрасывает этот срок.
Отмена запроса не запускает fallback. Отдельного определения VPN нет.

Успешно расшифрованные ошибки приложения (401/403/409/422/503 и другие) возвращаются
вызывающему коду; они не запускают повтор бизнес-действия через другой транспорт.
Сессия остаётся в зашифрованном запросе, поэтому вход сохраняется при смене канала,
а cross-site cookies не требуются. Оба канала используют прежнюю авторизацию API.

## Повторная доставка

Прямой health сообщает случайный идентификатор процесса и время сервера.
В шифрованный payload добавляется `delivery` с этим instanceId и сроком 90 с.
Оба канала попадают в один существующий replay store bridge: одинаковый id и
fingerprint получает тот же результат, даже если первый ответ потерялся.

После рестарта новый процесс отвергает старый instanceId с зашифрованным ответом
503 `RELAY_DELIVERY_UNCERTAIN`, **не исполняя запрос**. Просроченные envelopes также
не исполняются, даже после удаления записи из replay store (TTL 120 с).
Ограничение касается повторной доставки одного envelope; это не обещание exactly-once
для новых пользовательских запросов. Повтор прикладных очередей сохраняет их
существующие ключи идемпотентности. Неопределённый результат не маскируется успехом.
Старые клиенты без поля delivery продолжают работать через Storage как прежде.

## Сервер и границы

Caddy snippet `infra/yandex/direct-relay.caddy` импортируется внутри существующего
HTTPS-хоста. Открыты только два пути: health и request. Внутренние API/БД остаются
на loopback. CORS разрешает только origin Кабанды, Content-Type и POST; cookies
и произвольные браузерные origins не разрешаются. Ответы имеют no-store.
Остальные существующие маршруты Caddy сохраняются.

Большие тела/ответы продолжают использовать шифрованные presigned blobs в Storage.
Прямой канал убирает очередь Storage Relay для API-вызовов, но не делает отправку
медиа независимой от Object Storage.

## Проверки

Покрыты direct, Storage, потерянный direct-ответ, malformed ciphertext, отмена,
таймаут чтения тела, общий health-probe, cooldown/повторная проверка, CORS,
рестарт процесса и истечение replay TTL. Интеграционные тесты прогоняют вход,
чтение и загрузку бинарного медиа, мутацию и выход через настоящий API bridge.
Production smoke использует только health/чтение; поездку с двумя физическими
телефонами и конкретными операторами нужно проверять отдельно.

## Откат

Удалить VITE_DIRECT_RELAY_URL из следующей PWA сборки либо восстановить предыдущую
статику из снимка publisher. Старая API версия совместима с прежним PWA, но откат API
выполнять после отката PWA: новая direct delivery требует нового bridge. Для полного
отката удалить import snippet из Caddyfile и reload после validate. Данные БД не менялись.
